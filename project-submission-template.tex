\section*{Brief Description}
\addcontentsline{toc}{section}{Brief Description}

\begin{projectbox}{courseBlue}
This document presents \emph{Autonomous Software Development Team}, a bounded, multi-agent
system that takes a natural-language feature request from idea to reviewed, tested, working
code. Five role-scoped agents (Product Owner, System Architect, Coder, QA/Tester, Code
Reviewer) are orchestrated by Claude Code through a single slash command, with real test
execution, JSON-Schema-validated hand-offs at every stage boundary, and a bounded
reject/fix loop that escalates to a human instead of retrying forever.
\end{projectbox}

\begin{itemize}
  \item Explanations below are specific to this project and to the two example features built with it.
  \item The public source repository, the full audit log, and real pytest output are provided as evidence.
  \item The project uses a fixed multi-agent workflow (five cooperating Claude Code sub-agents) coordinated by one orchestrating slash command.
  \item No MCP servers, external APIs, or paid third-party services are used; only Claude Code sub-agents, plain Python, and the standard library.
  \item No secret keys, passwords, or personal data are included anywhere in the submitted files.
\end{itemize}

\section{Project Summary}
\sectionintro{Provide a general overview of the project in a few short paragraphs.}

\answerarea{The problem the project aims to solve}{
A realistic software feature request normally passes through several distinct roles --
product owner, architect, implementer, tester, and reviewer -- each with a different
responsibility and a different view of ``done.'' When a single AI agent is asked to play
all of these roles at once, its own approval of its own code is not a trustworthy signal:
there is no separation of concerns, no ground-truth verification step, and no defined
stopping condition if the agent keeps disagreeing with itself. This project addresses that
gap by splitting the process into five least-privilege agents with a real, executable test
suite as the ground truth, JSON-Schema validation at every hand-off, and an explicit,
bounded retry limit that hands control back to a human instead of looping indefinitely.
}

\answerarea{The purpose of the project and its target users}{
The purpose is to demonstrate a small but genuinely trustworthy autonomous development
pipeline: one that a developer could hand a feature request to and receive back either
working, reviewed code, or a clear, structured explanation of why it could not be produced
automatically. The target users are developers or teams who want repeatable,
auditable AI-assisted development -- with verifiable test results and an audit trail --
rather than a single opaque ``AI wrote this, trust it'' output.
}

\answerarea{Brief project summary: How does the system work overall, and what does it produce?}{
The system is implemented as five Claude Code sub-agents plus one orchestrating slash
command (\texttt{/build-feature}). A \emph{linear build phase} turns a raw feature
request into a schema-validated \texttt{requirements.md} (Product Owner) and then a
schema-validated \texttt{architecture.md} design proposal (System Architect); coding does
not start until this design exists. The Coder then implements the source code. From this
point a \emph{bounded, verified review loop} runs: the real \texttt{pytest} suite is
executed and converted into a ground-truth \texttt{test-results.json}; the QA/Tester
(read-only) inspects the code and test output for logic and security issues; the Code
Reviewer (read-only) makes the final approve/reject call, and any failing test is an
automatic reject regardless of the reviewer's own opinion. A rejection sends specific
feedback back to the Coder for another attempt, up to three attempts; if the third attempt
is also rejected, the system builds a structured \texttt{escalation.json} for a human
instead of retrying a fourth time. Every stage of every attempt is appended to an
append-only audit log (\texttt{logs/dev-team-audit.jsonl}). The output of a successful run
is working, tested source code plus the full paper trail (requirements, architecture, test
results, QA report, review verdict) that produced it.
}

\section{Input, Output, and Usage}
\sectionintro{Summarize what the system receives, what it produces, and how it is used.}

\answerarea{Primary inputs}{
A single natural-language feature request, either typed inline as an argument to the
\texttt{/build-feature} command or provided as a Markdown file (e.g.\ \texttt{feature-request.md})
describing the desired functionality, constraints, and any known edge cases.
}

\answerarea{Primary outputs}{
Working, tested source code approved by the Code Reviewer; the supporting documents
\texttt{requirements.md} and \texttt{architecture.md}; the ground-truth
\texttt{test-results.json}; the \texttt{qa-report.json} and \texttt{review-result.json};
and, only when the review loop is exhausted after three rejections, a structured
\texttt{escalation.json} describing exactly what a human needs to look at. Every stage is
also appended to \texttt{logs/dev-team-audit.jsonl} as a permanent audit trail.
}

\answerarea{Brief usage scenario: Main steps from the user request to the result}{
(1)~The user writes a feature request. (2)~The user runs
\texttt{/build-feature feature-request.md} inside Claude Code. (3)~Product Owner,
System Architect, and Coder run in sequence, each output validated against its JSON
Schema before the next stage may use it. (4)~The real \texttt{pytest} suite is executed
via \texttt{scripts/run\_tests.sh}, wrapped in \texttt{scripts/run\_with\_retry.py} for
bounded infrastructure retries. (5)~QA/Tester and Code Reviewer evaluate the current code
and test results. (6a)~If approved, the loop ends and the code is ready to use. (6b)~If
rejected and fewer than three attempts have been made, specific feedback is sent back to
the Coder and the loop repeats. (6c)~If the third attempt is also rejected, the system
builds \texttt{escalation.json} and stops instead of retrying again.
}

\answerarea{A sample input and its corresponding output}{
\textbf{Input:} ``Add a small, self-contained Python utility function that generates a
random password guaranteed to satisfy all five rules used by the existing
\texttt{password\_strength.py} checker, using cryptographically secure randomness.''\\[3pt]
\textbf{Output:} \texttt{password\_generator.py}, exposing
\texttt{generate\_password(length=12)}, approved by the Code Reviewer on the first
attempt with 33/33 pytest tests passing (see Section~6, Trial~4), together with
\texttt{requirements.md}, \texttt{architecture.md}, \texttt{test-results.json},
\texttt{qa-report.json}, and \texttt{review-result.json} for that run.
}

\section{System Design}
\sectionintro{Describe the architecture only to the extent that it applies to your project.}

\answerarea{Why did you choose this approach? Briefly justify the choice of an agent, workflow, or traditional software}{
A fixed, role-scoped multi-agent workflow was chosen over a single do-everything agent for
three reasons. First, \emph{least-privilege tool access} is only meaningful if roles are
genuinely separate: the QA/Tester has Read/Grep only and the Code Reviewer has Read only,
so neither can silently ``fix'' the code it is supposed to be gating -- a property a single
agent cannot have. Second, a \emph{fixed workflow with explicit stage boundaries} makes it
possible to validate each hand-off against a JSON Schema and fail fast at exactly the
boundary where something went wrong, instead of an error surfacing several steps later in a
confusing form. Third, \emph{real test execution} (an actual \texttt{pytest} run, not an
agent's self-report) gives a ground-truth signal that a failing test is always an automatic
reject, which removes an entire class of the "the agent approved its own mistake" failure
mode that a single-agent design is exposed to.
}

\answerarea{The system's main components and their responsibilities}{
\textbf{Product Owner} (Read/Write, own document only) turns the raw request into structured
\texttt{requirements.md}. \textbf{System Architect} (Read/Write, own document only) turns
requirements into a \texttt{architecture.md} design proposal -- a plan for approval, not
code. \textbf{Coder} (Read/Write, source files only, never test files) implements the
design and, on rejection, fixes only what was flagged. \textbf{QA/Tester} (Read/Grep only,
cannot modify anything) searches the code for logic and security issues and reports them.
\textbf{Code Reviewer} (Read only) makes the final approve/reject call using QA's report and
the ground-truth test results. Supporting these five agents: \texttt{scripts/} (schema
validation, the real test runner, bounded infra-retry, escalation building, and audit
logging) and \texttt{schemas/} (one JSON Schema per agent output).
}

\answerarea{The main data or task flow between components}{
\texttt{feature-request.md} $\rightarrow$ \texttt{requirements.md} (schema-validated)
$\rightarrow$ \texttt{architecture.md} (schema-validated) $\rightarrow$ Coder writes source
$\rightarrow$ \texttt{scripts/run\_with\_retry.py} wraps the real \texttt{pytest} run
$\rightarrow$ \texttt{test-results.json} (ground truth) $\rightarrow$ QA report
$\rightarrow$ Code Reviewer verdict (approved / rejected, with a confidence level)
$\rightarrow$ on rejection with attempts remaining, feedback loops back to the Coder; on the
third rejection, \texttt{scripts/build\_escalation.py} produces \texttt{escalation.json}
instead. Every stage of every attempt is appended to
\texttt{logs/dev-team-audit.jsonl}. See the diagram below.
}

source files only and is explicitly forbidden from touching test files; QA/Tester has

code, only describe what must change. Any failing test, or any high-severity security
finding from QA, is an automatic reject with no judgment call. The review loop is bounded
at three rejected attempts, after which the system escalates to a human instead of retrying
again. Pushing the finished project to the public GitHub repository was an explicit,
separate action confirmed with the project owner before it was carried out.
}

\answerarea{Brief installation and usage steps for running the project}{
(1)~Clone the repository and install the Python dependencies:
\texttt{pip install -r requirements-dev.txt}. (2)~Write the desired feature in a Markdown
file, e.g.\ \texttt{feature-request.md}. (3)~Inside Claude Code, in the project directory,
run \texttt{/build-feature feature-request.md}. (4)~Watch the linear build phase
(Product~Owner~$\rightarrow$~Architect~$\rightarrow$~Coder) run, followed by the bounded
review loop (Test~Runner~$\rightarrow$~QA~$\rightarrow$~Reviewer, up to three attempts).
(5)~Inspect \texttt{review-result.json} for the verdict, or \texttt{escalation.json} if the
loop was exhausted. (6)~Optionally push a \texttt{feature/**} branch to trigger the same
pipeline headlessly in GitHub Actions.
}

\answerarea{A significant technical problem encountered and the solution applied}{
The project's ground-truth test-execution script, \texttt{scripts/run\_tests.sh}, is a Bash
script invoked via a shebang line -- which works transparently on the Linux CI runner but
not on native Windows, where a shebang cannot be executed directly. Beyond that, the script
originally forwarded \texttt{pytest}'s raw exit code to the caller; since \texttt{pytest}
exits with code~1 whenever any test simply \emph{fails} (a completely normal outcome, not a
tooling crash), the bounded infra-retry wrapper \texttt{scripts/run\_with\_retry.py} was
misclassifying ordinary failing-test results as a transient infrastructure error, retrying
them needlessly, and ultimately routing them toward an infrastructure escalation instead of
letting the Code Reviewer make the intended automatic-reject decision. Both issues were
found only by actually executing the pipeline end-to-end, not by reading the code. The fix
was two-fold: \texttt{run\_with\_retry.py} now transparently prepends \texttt{bash} for any
\texttt{.sh} command on Windows, and \texttt{run\_tests.sh} now treats \texttt{pytest} exit
codes~0 and~1 as a successful run of the \emph{test runner} itself (only codes greater than
1 -- usage errors, internal errors, no tests collected -- are treated as real infrastructure
failures), so a failing test now correctly reaches the review loop as an ordinary, expected
rejection instead of being swallowed by the infra-retry path.
}

No end-user personal data is processed by this project at all -- its two example features
operate only on password strings supplied directly by a caller and never log, print, or
persist them. Because the example domain is password handling, randomness quality was

scoped to the minimum its role requires (Section~4), destructive git operations were never
used, and the one action with external, hard-to-reverse effect in this project -- pushing
the repository to the public GitHub remote -- was explicitly confirmed with the project
owner before being carried out rather than performed automatically. No third-party code,
datasets, or copyrighted material are included in the submission.

\section{Conclusion and Future Work}

\answerarea{The most important results and learning outcomes obtained from the project}{
The most important result is that the bounded, schema-gated, multi-agent review loop was
not just designed but actually built and exercised end-to-end, including its least-common
paths: a genuine reject-and-fix cycle and a genuine three-strikes escalation, both driven by
real agents and a real test suite rather than scripted or simulated for the demonstration.
A second, unplanned but valuable outcome was that running the system for real -- rather than
only reading or reasoning about the code -- surfaced two real defects in the orchestration
scripts themselves (Section~5), reinforcing that execution-based verification catches classes
of bugs that code review alone does not.
}

\answerarea{Improvements that could be made with more time}{
With more time, the next steps would be: exercising the GitHub Actions headless path for
this same submission rather than only the local run; extending the pipeline to a multi-file
feature and to one with a user-facing interface, to test whether the current agent
boundaries still hold at larger scope; adding an automated regression check for the two
Windows-specific script fixes so they cannot silently regress; and adding lightweight
per-stage cost/token tracking to the audit log so the loop's efficiency, not just its
correctness, can be measured over many runs.
}

\answerarea{Core course concepts applied in the project}{
Multi-agent orchestration with clearly separated roles; least-privilege permission
boundaries enforced per agent; structured, schema-validated inter-agent communication with
fail-fast validation at every hand-off; bounded autonomous loops with an explicit stopping
condition and human escalation; the distinction between a normal rejection and an
infrastructure failure, with separate, appropriately-sized retry policies for each;
graceful degradation when an agent's own output cannot be trusted; and observability via a
complete, append-only audit log.
}
